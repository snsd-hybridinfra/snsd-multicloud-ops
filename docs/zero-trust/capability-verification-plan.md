# Zero Trust Capability Verification Plan

This plan covers all 44 capabilities classified as laboratory-implementable or partially laboratory-implementable. Reference-only capabilities are excluded from execution and remain in the backlog. Every test is approval-gated; **FAILURE_INJECTION** and **ADVERSARIAL_TEST** are not authorized by this document.

## Validation method vocabulary

- `STATIC_REVIEW`, `CONFIGURATION_CHECK`, `RUNTIME_OBSERVATION`, `ACCESS_TEST`, `POLICY_TEST`, `NEGATIVE_TEST`, `FAILURE_INJECTION`, `RECOVERY_TEST`, `CONTINUOUS_MONITORING`, `ADVERSARIAL_TEST`.
- Destructive testing requires explicit human approval, an isolated target, and a tested rollback. Default execution is non-destructive.
- Evidence authority is the test operator plus repository maintainer review; self-generated output is not accepted without sanitization and expected/observed comparison.

## Common acceptance rules

A capability remains `UNASSESSED` until its preconditions, positive and required negative paths, evidence authority, cleanup, and limitations are accepted. `PARTIAL` evidence cannot support `VALIDATED` status. Raw output, credentials, state, private keys, kubeconfig, unique cloud identifiers, and sensitive packet data must not be committed.
